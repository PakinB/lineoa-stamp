# เดลิเวอรี่ร้าน La-Mi — การออกแบบ

> สถานะ: **เขียนเสร็จและขึ้น production แล้ว** · 13 ต.ค. 2026
> ใช้ฐานเดียวกับระบบบัตรสะสม (ดู `docs/design.md`) · ร่างหน้าจอ 12 จอเคาะแล้วก่อนเขียนโค้ด

ลูกค้าสั่งผ่าน LIFF ในแชท LINE แล้ว**พนักงานร้านขับไปส่งเอง ไม่มีไรเดอร์** —
แทนการรับโทรศัพท์แล้วจดใส่กระดาษ

## 2. ⚠️ กติกาที่เปลี่ยนไปจากเดิม

`CLAUDE.md` เคยล็อกไว้ว่า **"ไม่เก็บเบอร์โทร"** — เดลิเวอรี่เลี่ยงไม่ได้ เจ้าของเคาะแล้ว 13 ต.ค. 2026

**เก็บที่ออเดอร์ ไม่ใช่ที่ตัวลูกค้า** — ลบออเดอร์เก่าทิ้งแล้วข้อมูลส่วนตัวหายไปด้วย
ทำให้ทำตาม PDPA ง่ายกว่ามาก · ระบบบัตรสะสมยังไม่เก็บเหมือนเดิม

**ผลตามมา:** ต้องทำหน้านโยบายความเป็นส่วนตัวและช่องทางขอลบข้อมูลจริง ยังค้างอยู่

## 3. การคิดเงิน — อยู่ในฐานข้อมูลทั้งหมด

```
ราคาหมาล่า  = (กรัม ÷ 100) × 45
ส่วนลด      = ปัดลงเป็นจำนวนเต็มบาท ของค่าอาหาร
ยอดชำระ     = ค่าอาหาร + ค่าส่ง − ส่วนลด
```

**หน้าเว็บไม่คำนวณเองสักบรรทัด** ทุกครั้งที่ตะกร้าหรือโซนเปลี่ยน จะยิง
`/api/delivery/quote` แล้ววาดตามที่ได้มา — ราคาที่ลูกค้าเห็นกับที่เก็บเงินจึงตรงกันเสมอ
เพราะใช้ฟังก์ชัน `delivery_calc()` ตัวเดียวกันทั้งตอนดูราคาและตอนสั่งจริง

ส่วนลดปัดลง เช่น 10% ของ 425 = 42.5 → ลดจริง 42 บาท
**ไม่มีเศษสตางค์** ตามที่เจ้าของไม่เอา และไม่ลดเกินเปอร์เซ็นต์ที่ประกาศ

**กรองค่าปลอมจากเบราว์เซอร์** — ชื่อวัตถุดิบที่ไม่มีในเมนูถูกทิ้ง · จำนวนถูกบีบ 1–10 ·
ราคาที่ส่งมาไม่มีผลเพราะคิดใหม่หมด

## 4. ส่วนลด

ตาราง `delivery_discounts` มีช่วงเวลาในตัว **หมดอายุเองโดยไม่ต้องมีใครไปปิด**

ตัวแรก: `ส่วนลดเปิดร้าน 10%` ลดค่าอาหาร 1 ต.ค. – 1 พ.ย. 2026 (เวลาไทย)

เดือนถัดไปเจ้าของสร้างตัวใหม่จาก `/admin/delivery` ได้เอง ไม่ต้อง deploy

⚠️ **เปอร์เซ็นต์กับช่วงเวลาแก้ย้อนหลังไม่ได้** เพราะออเดอร์เก่าผูกส่วนลดตัวนั้นไว้
รายงานย้อนหลังจะไม่ตรงกับที่เก็บเงินจริง — อยากเปลี่ยนให้ปิดตัวเก่าแล้วสร้างใหม่

ลดเฉพาะ **ค่าอาหาร** ไม่ลดค่าส่ง เพราะค่าส่งเป็นต้นทุนที่ร้านจ่ายจริง (ปรับได้ที่ `applies_to`)

## 5. การชำระเงิน

**QR พร้อมเพย์สร้างในเครื่องลูกค้า** (`lib/promptpay.ts`) ไม่ผ่านตัวกลาง จึงไม่เสียค่าธรรมเนียม
เขียนเองตามมาตรฐาน EMVCo ทดสอบ CRC16 กับค่าตรวจมาตรฐาน `0x29B1` แล้ว

เบอร์พร้อมเพย์อยู่ใน `app_settings.promptpay_id` **ไม่ฝังในโค้ด** เพราะเป็นเบอร์จริงของร้าน
และ repo นี้ push ขึ้น GitHub

### ตรวจสลิปแบบที่ฟรีและได้ผลจริง

```
ลูกค้าแนบสลิป
  → ย่อรูปในมือถือเหลือราว 80 KB
  → อ่าน QR ท้ายสลิปด้วย jsQR ได้เลขอ้างอิง
  → เลขอ้างอิงซ้ำกับที่เคยใช้ = ปฏิเสธทันที (unique index บน slip_ref)
  → พนักงานเปิดดูรูป เทียบกับแอปธนาคาร แล้วกดยืนยัน
```

**ระบบเช็คได้แค่ว่าสลิปไม่ซ้ำ ไม่ได้ยืนยันว่าเงินเข้า** — หน้าพนักงานเขียนเตือนไว้ตัวโต
ไม่ให้เข้าใจผิดว่าระบบตรวจให้แล้ว

⚠️ **ออเดอร์ที่โอนเงินกดรับไม่ได้จนกว่าจะยืนยันว่าเงินเข้า** บังคับในฐานข้อมูล ไม่ใช่ซ่อนปุ่ม

## 5'. จ่ายปลายทางต้องปลดล็อกก่อน

```
ส่งสำเร็จ 0 ครั้ง  →  เลือกได้เฉพาะโอนพร้อมเพย์
ส่งสำเร็จ ≥ 1 ครั้ง →  เลือกปลายทางได้
```

นับจากออเดอร์ที่ **`status = 'delivered'` จริง** ไม่ใช่ออเดอร์ที่สั่ง — ไม่งั้นกดสั่งแล้ว
ยกเลิกเองก็ผ่านด่านได้ (ทดสอบเคสนี้แล้ว)

บังคับสองชั้น: ฐานข้อมูลปฏิเสธด้วย `cod_locked` และหน้าลูกค้าซ่อนตัวเลือกพร้อมบอกเหตุผล
*"สั่งครั้งแรกโอนก่อนนะ — ส่งถึงแล้วครั้งหน้าจ่ายปลายทางได้เลย"*
**ซ่อนปุ่มอย่างเดียวไม่พอ** ใครแก้คำขอส่ง `pay_method=cod` มาเองก็ยังถูกปฏิเสธ

ปรับได้ที่ `app_settings.delivery_cod_after_orders` จากหน้าแอดมิน · ตั้ง `0` คือปิดกติกานี้

## 6. ลำดับสถานะ

```
placed → accepted → cooking → out → delivered
                                       └─ ปั๊มสแตมป์ 1 ดวงอัตโนมัติ
ยกเลิกได้ทุกขั้นก่อน delivered
```

ข้ามขั้นไม่ได้ · `out` ต้องระบุคนขับ · `delivered` ต้องมีคนขับและเวลา (CHECK constraint)

**ปั๊มสแตมป์ผ่าน `award_stamp()` พร้อมกุญแจกันซ้ำ `dorder:<id>`** กดสองทียังได้ดวงเดียว
(หลักการข้อ 2 — ห้าม INSERT ลง ledger ตรง ๆ)

## 7. ที่เก็บรูปสลิป — ของชั่วคราว

เก็บลง Postgres (`delivery_slips`) เพราะ bucket ของ Supabase ต้องมี service key
และ R2 ต้องสร้าง bucket จากบัญชีจริงก่อน — เก็บในฐานข้อมูลไปก่อนจะได้ไม่ต้องรอ

คุมขนาดสามชั้น: ย่อรูปในมือถือ · CHECK ไม่เกิน 200 KB · `api_admin_purge_old_slips(90)`
ลบรูปที่ปิดงานแล้วเกิน 90 วัน — ลบได้เพราะตัวกันสลิปซ้ำคือ `slip_ref` ที่เก็บแยกไว้

**ย้ายไป object storage ได้โดยไม่ต้องแก้หน้าจอ** เพราะเข้าถึงผ่าน API เส้นเดียว

## 8. ⚠️ กับดักที่เจอตอนเขียน — เสียเวลาไปมาก

**postgres.js แปลงค่าเป็น JSON ให้เองเมื่อพารามิเตอร์ปลายทางเป็น `jsonb`**

ถ้าฝั่งแอปทำ `JSON.stringify()` มาก่อนแล้ว จะกลายเป็น**สตริงซ้อนสตริง** —
`jsonb_array_length()` พังด้วย *"cannot get array length of a scalar"*

```
ผิด   api_xxx(p_items jsonb)  +  ${JSON.stringify(items)}   → jsonb เป็น string
ถูก   api_xxx(p_items text)   +  ${JSON.stringify(items)}   → cast เองข้างใน
```

**ฟังก์ชันที่รับ JSON จากฝั่งแอปต้องรับเป็น `text` แล้ว `::jsonb` เองข้างใน**
แพตเทิร์นนี้คือที่ `api_admin_save_all_rewards` ใช้มาตั้งแต่ 0005 และทำงานถูกมาตลอด

บั๊กเดียวกันนี้ซ่อนอยู่ใน `api_admin_update_setting` มาตลอด — กดบันทึกที่หน้า
`/admin/settings` แล้วค่าจะกลายเป็นข้อความ `"10"` แทนตัวเลข `10` จากนั้นทุกที่ที่
อ่านค่าด้วย `value::int` จะพัง **แปลว่าออก QR ไม่ได้ทั้งร้าน** · แก้แล้วใน `0020`
ตรวจแล้วว่ายังไม่มีค่าไหนเสียหาย เพราะยังไม่เคยมีใครกดบันทึกสำเร็จ

## 11. ที่ยังไม่ได้ทำ

- หน้า `/privacy` `/terms` และช่องทางขอลบข้อมูล — **จำเป็นขึ้นมากหลังเก็บที่อยู่/เบอร์**

- รวมยอดเดลิเวอรี่เข้ารายงาน Excel
- LIFF app ตัวที่สอง + ปุ่มริชเมนู (งานในคอนโซล ไม่ใช่โค้ด)
