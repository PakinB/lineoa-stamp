# POS ร้าน La-Mi — ร่างการออกแบบ

> สถานะ: **ร่าง** ยังไม่ได้เขียนโค้ด · รอยืนยันเรื่องเครื่องพิมพ์ก่อน
> เชื่อมกับระบบสแตมป์ที่ใช้งานอยู่แล้วผ่าน `POST /v1/tokens` (ดู `docs/design.md` §10)

---

## 1. ข้อสรุปที่ตกลงแล้ว

| เรื่อง | ตัดสินใจ | เหตุผล |
|---|---|---|
| เครื่องชั่ง | **พนักงานอ่านแล้วกรอกเอง** | ไม่ต้องต่อสายอะไร เริ่มได้ทันที |
| รับเงิน | **PromptPay QR ล็อคยอด สร้างเอง** | ฟรี ไม่ต้องผ่านตัวกลาง |
| รู้ว่าเงินเข้า | **แอป/กล่องเสียงของธนาคาร** แล้วพนักงานกดยืนยัน | payment gateway คิด 1.5–1.8% = ~99,000 ฿/เดือนที่ขนาดร้านนี้ |
| ใบเสร็จ | **พิมพ์กระดาษ** ผ่านเครื่องพิมพ์ Bluetooth (ESC/POS) | เว็บสั่งได้ตรงผ่าน Web Bluetooth ไม่ต้องเขียนแอป Android |
| สแตมป์ | เรียก API ของระบบเดิม | ไม่ต้องแก้ระบบสแตมป์เลย |

**ที่ตั้งใจไม่ทำ:** payment gateway · ต่อเครื่องชั่งอัตโนมัติ · แอป Android · เครื่องพิมพ์ในตัว Ocha

## 2. Flow หน้าร้าน

```
1  ลูกค้าชั่งของ                    พนักงานอ่านตัวเลขจากเครื่องชั่ง
2  กรอกน้ำหนัก + เลือกน้ำซุป         POS คำนวณราคาให้
3  เพิ่มเครื่องดื่ม/ของอื่น           สรุปรายการขึ้นจอ
4  หันจอให้ลูกค้าดู                  ← ลูกค้าเห็นรายการกับยอดก่อนจ่าย
       380 ก. ซุปมาล่าเผ็ดกลาง  228.-
       โค้ก 1 กระป๋อง             19.-
       รวม                      247.-
       [ QR พร้อมเพย์ ล็อคยอด 247 ]
5  ลูกค้าสแกนจ่าย                   เงินเข้าบัญชีร้านตรง ๆ
6  แอป/กล่องธนาคารพูด               "เงินเข้าแล้ว 247 บาท"
7  พนักงานกด "รับเงินแล้ว"           บันทึกว่าใครเป็นคนกดยืนยัน
8  พิมพ์ใบเสร็จ                      ออกจากเครื่องพิมพ์ Bluetooth
9  จอขึ้น QR สะสมสแตมป์              เรียก POST /v1/tokens ของระบบเดิม
10 ลูกค้าสแกน → ได้ดวง               จอเปลี่ยนเป็น "✓ ได้ดวงที่ 7" เอง
```

**ข้อ 4 สำคัญที่สุดสำหรับลูกค้า** — เห็นว่าจ่ายค่าอะไรก่อนเงินออกจากกระเป๋า
ไม่ใช่มารู้ทีหลังตอนได้ใบเสร็จ

**ข้อ 7 สำคัญที่สุดสำหรับเจ้าของ** — ระบบเชื่อพนักงาน จึงต้องบันทึกไว้ว่าใครกด
และต้องมีการกระทบยอดรายวัน (ดู §4)

### เมื่อไม่เป็นไปตามแผน

| สถานการณ์ | ทำยังไง |
|---|---|
| ไม่ได้ยินเสียงใน ~10 วินาที | ดูแอปธนาคาร หรือขอดูสลิปในมือถือลูกค้า |
| ลูกค้าจ่ายเงินสด | เลือกวิธีจ่าย "เงินสด" ข้ามขั้นที่ 4–6 |
| เครื่องพิมพ์ไม่ทำงาน | ปิดบิลได้ตามปกติ พิมพ์ซ้ำทีหลังได้จากประวัติ |
| ลูกค้าไม่สแกนสแตมป์ | ข้ามไป อย่าให้คิวติด |
| เน็ตหลุด | **ต้องขายต่อได้** — ดู §5 |

## 3. สิ่งที่ต้องบันทึกทุกบิล

```
order
  id, branch_id, order_no, opened_at, closed_at
  items[]        ชื่อ, จำนวน/น้ำหนัก, ราคาต่อหน่วย, รวม
  subtotal, discount, total
  payment_method  promptpay | cash
  paid_at
  confirmed_by    ← พนักงานที่กดยืนยันรับเงิน (บังคับ)
  stamp_token     รหัส QR สแตมป์ที่ออกให้บิลนี้
  printed_at      พิมพ์ใบเสร็จแล้วหรือยัง
  voided_at, void_reason, voided_by
```

`confirmed_by` เป็นหัวใจของการตรวจสอบย้อนหลัง — เก็บตั้งแต่บิลแรก
เพิ่มทีหลังจะไม่มีข้อมูลย้อนหลังให้ไล่

## 4. Dashboard กระทบยอดรายวัน

### ปัญหาที่ต้องแก้

POS เชื่อพนักงานว่าเงินเข้าแล้ว **ไม่มีอะไรยืนยันอัตโนมัติ**
จึงต้องเทียบกับความจริงนอกระบบวันละครั้ง

### สิ่งที่ระบบรู้เอง

| ตัวเลข | มาจากไหน |
|---|---|
| ยอดขายรวมวันนี้ | รวม `orders.total` |
| แยกตามวิธีจ่าย | พร้อมเพย์ / เงินสด |
| แยกตามพนักงาน | `confirmed_by` |
| จำนวนบิล · บิลเฉลี่ย | นับจาก orders |
| บิลที่ยกเลิก | `voided_at` |

### สิ่งที่ต้องกรอกจากนอกระบบ (สิ้นวัน)

| ช่อง | เอามาจากไหน |
|---|---|
| ยอดเงินเข้าบัญชีวันนี้ | แอปธนาคาร / K SHOP / ถุงเงิน |
| เงินสดในลิ้นชัก | นับตอนปิดร้าน |

### หน้าตาผลลัพธ์

```
┌─ กระทบยอด 15 ก.ย. 2026 · สาขาลาดพร้าว ────────────┐
│                                                    │
│  พร้อมเพย์                                          │
│    ยอดใน POS              18,420.-                 │
│    เงินเข้าบัญชีจริง        18,420.-                 │
│    ผลต่าง                       0.-   ✓ ตรง        │
│                                                    │
│  เงินสด                                            │
│    ยอดใน POS               3,180.-                 │
│    นับได้จริง               3,100.-                 │
│    ผลต่าง                     −80.-   ⚠ ขาด       │
│                                                    │
│  รวมยอดขาย  21,600.-   ·   64 บิล   ·   เฉลี่ย 338.-│
└────────────────────────────────────────────────────┘
```

**ถ้าผลต่างไม่เป็นศูนย์ ต้องคลิกดูรายบิลได้ทันที** เรียงตามเวลา แสดงว่าใครเป็นคนยืนยัน
นี่คือสิ่งที่ทำให้หน้านี้เป็นเครื่องมือ ไม่ใช่แค่รายงาน — ตัวเลขผลต่างคือตัวสินค้า

### สัญญาณที่ควรเตือนอัตโนมัติ

| สัญญาณ | แปลว่าอะไร |
|---|---|
| พร้อมเพย์ต่างจากบัญชีเกิน 1 บิล | มีบิลที่กดยืนยันแต่เงินไม่เข้าจริง |
| เงินสดขาดเกินเกณฑ์ | ทอนผิด หรือมีปัญหา |
| พนักงานคนหนึ่งยกเลิกบิลบ่อยผิดปกติ | ควรดูละเอียด |
| บิลที่ยืนยันห่างจากเวลาเปิดบิลนานผิดปกติ | อาจกดย้อนหลัง |

### เชื่อมกับระบบสแตมป์

หน้าเดียวกันแสดงตัวเลขจากระบบสแตมป์ที่มีอยู่แล้วได้เลย:

- QR สแตมป์ที่ออก vs ถูกสแกนจริง (จาก `api_shift_summary`)
- **อัตราสแกนต่อบิล** = QR ที่ถูกสแกน ÷ จำนวนบิล
  ต่ำกว่า 30% แปลว่าพนักงานไม่ได้ยื่นให้ลูกค้าจริง (ดู `docs/design.md` §12)
- รางวัลที่จ่ายไปวันนี้

## 5. ข้อจำกัดที่ต้องออกแบบรับตั้งแต่แรก

**ต้องขายได้ตอนเน็ตหลุด** — ร้านอาหารหยุดขายไม่ได้
ถ้า POS เป็นเว็บล้วน เน็ตหลุดแล้วจบ ต้องคิดเรื่องนี้ก่อนเขียนบรรทัดแรก
(เก็บบิลไว้ในเครื่องก่อนแล้วค่อยส่งขึ้นเมื่อเน็ตกลับมา)

**Web Bluetooth ต้องให้คนกดเลือกเครื่องพิมพ์** เบราว์เซอร์บังคับ ปิดไม่ได้
ถ้าจำอุปกรณ์ไม่ได้ พนักงานต้องเลือกใหม่ตอนเข้ากะ — ยังไม่ได้ทดสอบ

**เครื่องพิมพ์ต้องพิมพ์ไทยได้** (CP874/TIS-620) รุ่นถูกบางตัวพิมพ์ไทยเป็นขยะ

> ทั้งสามข้อต้องพิสูจน์ด้วยของจริงก่อนลงแรงเขียน POS เต็มรูปแบบ

---

## 6. ขั้นถัดไป

1. ซื้อเครื่องพิมพ์ Bluetooth มาหนึ่งตัว
2. ทำหน้าทดสอบพิมพ์ใบเสร็จตัวอย่าง — ตอบสามคำถาม: สั่งได้ไหม · จำอุปกรณ์ได้ไหม · ไทยออกถูกไหม
3. ผ่านแล้วค่อยเขียน POS เต็มรูปแบบ · ไม่ผ่านค่อยเปลี่ยนไปทางแอป Android ตั้งแต่ต้น
