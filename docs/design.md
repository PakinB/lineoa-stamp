# เอกสารออกแบบระบบบัตรสแตมป์ร้านหมาล่า

> ฉบับในรีโปนี้เป็น **แหล่งความจริง** — อัปเดตล่าสุด 6 กันยายน 2026
> (เวอร์ชันนำเสนอบนเว็บอยู่ที่ artifact แต่ค้างอยู่หลายจุด ให้ยึดไฟล์นี้)

บัตรสะสม 10 ดวงบน LINE สำหรับร้านหมาล่า 2–5 สาขา · 1 บิล = 1 ดวง ·
รางวัลเป็น checkpoint บนบัตร · ไม่มีวันหมดอายุ · ใช้ข้ามสาขาได้ · ไม่ใช้กระดาษ

---

## 1. ข้อสรุปการออกแบบ

| เรื่อง | การตัดสินใจ | เหตุผล |
|---|---|---|
| หน่วยสะสม | สแตมป์ ไม่ใช่แต้ม · 1 บิล = 1 ดวง | อธิบายได้ในประโยคเดียว ไม่ต้องอ่านยอดเงินจาก POS |
| ขั้นต่ำ | ไม่มี ทุกบิลได้ดวง | ลดการตัดสินใจของพนักงานหน้างาน |
| บิลแยก | แยกจ่าย 3 บิล = 3 ดวง คนละคน | ระบบไม่ต้องรู้จักโต๊ะ |
| รางวัล | แปะเป็น checkpoint บนบัตร (ช่อง 5 และ 10) | สิทธิ์เกิดเองตอนปั๊มถึง ลูกค้าไม่ต้องกดแลก |
| ใครเลือกของ | พนักงานเลือกให้ที่หน้าร้าน | ตัดระบบสต็อกของรางวัลออกทั้งก้อน |
| อายุ | สแตมป์และสิทธิ์ไม่มีวันหมดอายุ | ตัดงานตามเวลาและเรื่องร้องเรียน |
| ข้ามสาขา | กระเป๋าเดียว ไม่เคลียร์ยอดกัน | `branch_id` เก็บไว้ดูสถิติเท่านั้น |
| ตัวตนลูกค้า | LINE userId อย่างเดียว ไม่เก็บเบอร์ ไม่มี OTP | ดู §6 |
| POS | ระบบยืนได้ด้วยตัวเอง เปิด REST API รอไว้ | บางสาขาจะทำ POS เอง บางสาขาไม่ใช้เลย |
| กระดาษ | ไม่ใช้เลยทุกช่องทาง | ข้อกำหนดจากเจ้าของ |

## 2. บัตรสแตมป์และ checkpoint

- บัตร 1 ใบ = **10 ช่อง** (ค่าจาก `app_settings.card_size`, ล็อกตอนเปิดบัตร)
- ครบ 10 → ปิดใบ **เปิดใบใหม่อัตโนมัติทันที** ดวงที่ 11 ลงใบที่ 2 ช่องที่ 1
- **checkpoint** คือช่องที่มีรางวัลแปะอยู่ — รางวัลจริงของร้าน:

  | ช่อง | รางวัล |
  |---|---|
  | 6 | โค้กฟรี 1 ขวด |
  | 8 | เฉาก๋วยฟรี |
  | 10 | หมาล่าฟรี 300 กรัม |

  รางวัลถี่ขึ้นในครึ่งหลังของบัตร ช่วงที่ลูกค้าใกล้ถึงเป้าและมีแรงจูงใจสูงสุด
- ปั๊มถึงช่อง checkpoint → ระบบสร้าง **สิทธิ์ (entitlement)** ให้อัตโนมัติ
- สิทธิ์จากบัตรใบเก่าที่ยังไม่ได้ใช้ ยังใช้ได้ตลอด

แก้ตำแหน่ง checkpoint และชื่อรางวัลได้จากตาราง `reward_checkpoints` โดยไม่ต้องแก้โค้ด

### ทำไมพนักงานเป็นคนเลือกของ

ถ้าให้ลูกค้าเลือกในแอป ระบบต้องรู้ว่า*สาขานี้ ตอนนี้ ของชิ้นไหนเหลือ* = ต้องทำสต็อกรายสาขา
แบบเรียลไทม์ และรับมือกรณีลูกค้าเลือกของที่เพิ่งหมด

**คนที่รู้ว่าของอะไรเหลือ คือคนที่ยืนอยู่หน้าตู้** ระบบมีหน้าที่แค่ยืนยันว่า "คนนี้มีสิทธิ์จริง
1 สิทธิ์" แล้วบันทึกว่าสุดท้ายให้ของอะไรไป `reward_options` จึงเป็นแค่ตัวเลือกให้พนักงานกด
ไม่ใช่สต็อกที่ต้องแม่นยำ

ปกติ checkpoint ละ 1 ตัวเลือก (หน้าจอพนักงานจึงเป็นปุ่มเดียว) แต่ตารางรองรับหลายตัวเลือกไว้
**เผื่อวันไหนโค้กหมด** เจ้าของเพิ่มของทดแทนได้จากหน้าแอดมินทันที ไม่ต้องรอ deploy

## 3. หลักการที่ทำให้ระบบไม่พังตอนโต

1. **บัญชีแยกประเภทเดียว ไม่มียอดลอย** — `stamp_ledger` เป็น append-only (มี trigger บังคับ)
   `stamp_cards.filled` เป็นแคช ถ้าไม่ตรงกันให้เชื่อ ledger
2. **ทุกการเขียนต้องกดซ้ำได้โดยผลไม่เปลี่ยน** — `idempotency_key` บนทุกดวง
   ตอนสแกนคือรหัส QR ตอนเดลิเวอรี่คือ id ของคำขอ
3. **สาขาไม่มีสิทธิ์แก้บัตร** — ปั๊มด้วยมือต้องเป็นระดับ manager ขึ้นไป บังคับกรอกเหตุผล
   (`source='manual'` มี CHECK constraint บังคับ)

## 4. เส้นทางลูกค้า

### ก. สะสมสแตมป์ (หน้าร้าน)

1. พนักงานกด "ออก QR" ตอนเก็บเงิน → รหัสสุ่ม 16 ตัว อายุ 10 นาที
2. ลูกค้าสแกนด้วยกล้อง LINE → เปิด LIFF → ล็อกอินอัตโนมัติ
3. ระบบเคลมรหัสแบบล็อกแถว → ปั๊มดวง → เช็ค checkpoint → คืนสถานะบัตร
4. ลูกค้าเห็นบัตรเต็มจอทันที พร้อมอนิเมชั่นดวงที่เพิ่งได้

**อนิเมชั่นตอนสแกนเสร็จ** — จังหวะนี้คือช่วงที่ลูกค้ารู้สึกดีที่สุด คุ้มที่จะทำให้ดี
API คืน `stamped_slot`, `card_completed` และ `new_entitlements` มาให้ครบ
เพื่อให้หน้าเว็บรู้ว่าต้องเล่นอะไร โดยไม่ต้องคำนวณเอง:

| จังหวะ | ข้อมูลที่ใช้ | สิ่งที่เล่น |
|---|---|---|
| ได้ดวงปกติ | `stamped_slot` | ดวงปั๊มลงมาที่ช่องนั้น |
| ถึง checkpoint | `new_entitlements` ไม่ว่าง | ดวงเปล่งแสง + ประกาศชื่อรางวัล |
| บัตรเต็ม | `card_completed` | บัตรปิด แล้วใบใหม่เลื่อนเข้ามา |

ข้อควรระวัง:

- **`stamped_slot` ต้องมาจากเซิร์ฟเวอร์** ห้ามให้หน้าเว็บ diff เอง เพราะลูกค้าเปิดหน้า
  จากการสแกน QR ตรง ๆ จะไม่มีสถานะก่อนหน้าให้เทียบ
- **เล่นหลังได้คำตอบแล้วเท่านั้น** ห้ามเล่นแบบ optimistic เพราะอาจล้มเหลวจากรหัสถูกใช้ไปแล้ว
  หรือติดเพดานต่อวัน แล้วจะกลายเป็นการหลอกลูกค้า
- **ใช้ CSS animation พอ ไม่ต้องลงไลบรารี** ลูกค้ายืนรออยู่หน้าเคาน์เตอร์
  ทุกกิโลไบต์ที่ LIFF ต้องโหลดคือเวลาที่เขายืนรอ
- **เคารพ `prefers-reduced-motion`** และอย่าให้อนิเมชั่นบล็อกการอ่านผล
  ต้องกดข้ามหรือเห็นผลลัพธ์ได้ทันทีถ้าไม่อยากรอ

### ข'. เส้นทางพนักงาน — สาขาที่ไม่มี POS

อุปกรณ์ที่ต้องมี: **มือถือหรือแท็บเล็ตหนึ่งเครื่องที่แคชเชียร์** ไม่ต้องมีเครื่องสแกน
ไม่ต้องมีเครื่องพิมพ์ ไม่ต้องลงแอป — เปิดเว็บ `staff.<โดเมน>` ค้างไว้ทั้งกะ

#### เริ่มกะ

ใส่ PIN 6 หลักครั้งเดียว เซสชันอยู่ยาวทั้งกะ ไม่ต้องใส่ซ้ำทุกบิล

> PIN ผูกกับตัวบุคคล ทุก QR ที่ออกจะบันทึก `issued_by` ไว้ ถ้าพนักงาน B มาใช้เครื่อง
> ที่ A ล็อกอินค้างไว้ การระบุตัวจะเพี้ยน — ที่ขนาด 2–5 สาขายอมรับได้
> เพราะทางเลือกคือใส่ PIN ทุกบิลซึ่งช้าเกินจะใช้จริง

#### วงจรหลัก — ต้องจบใน 15 วินาที

1. ลูกค้าจ่ายเงินเสร็จ **พนักงานเป็นฝ่ายเสนอก่อน** ไม่ต้องรอลูกค้าถาม
2. กดปุ่มเดียว → QR ขึ้นเต็มจอ
3. หันจอให้ลูกค้าสแกนด้วยกล้อง LINE
4. **หน้าจอพนักงานเปลี่ยนเป็น "✓ ได้ดวงที่ 7 แล้ว" เอง** → กดถัดไป

ช่องใส่เลขบิลมีให้แต่**ข้ามได้** สาขาที่ไม่มี POS ส่วนใหญ่ไม่มีเลขบิลจะให้ใส่อยู่แล้ว
ใส่ก็ต่อเมื่ออยากกระทบยอดย้อนหลังเท่านั้น

> **จุดที่มักออกแบบพลาด:** ถ้าหน้าจอพนักงานไม่บอกว่าลูกค้าสแกนสำเร็จหรือยัง
> พนักงานจะไม่กล้าเก็บจอ ต้องยืนถามลูกค้าว่า "ได้หรือยังคะ" ทุกครั้ง ซึ่งทำให้คิวติด
> หน้า QR ต้องคอยเช็คสถานะเอง (poll ทุก 2 วินาทีพอ ไม่ต้องใช้ websocket ที่สเกลนี้)
> แล้วเปลี่ยนหน้าจอทันทีที่รหัสถูกเคลม

#### ลูกค้ามารับรางวัล

1. พนักงานกด **"รับรางวัล"** → QR ขึ้นเต็มจอ
2. ลูกค้าสแกน แล้วแตะเลือกสิทธิ์บนมือถือตัวเอง
3. จอพนักงานขึ้น "✓ ให้โค้กฟรี 1 ขวด กับคุณพิมพ์" เอง → หยิบของให้ → จบ

พนักงานไม่ต้องพิมพ์อะไรเลย เป็นท่าเดียวกับตอนออก QR สะสมทุกประการ
ถ้าลูกค้ากดพลาด กด "คืนสิทธิ์" ได้ภายใน 10 นาที

#### เมื่อไม่เป็นไปตามแผน

| สถานการณ์ | ทำยังไง |
|---|---|
| ลูกค้าไม่มี LINE / ไม่สนใจ | ข้ามไป อย่าให้คิวติด |
| มือถือลูกค้าแบตหมด เน็ตไม่มี | ข้ามไป หรือจดไว้ให้ผู้จัดการปั๊มย้อนหลังภายใน 7 วัน |
| เน็ตร้านล่ม ออก QR ไม่ได้ | จดจำนวนบิลไว้ ผู้จัดการปั๊มย้อนหลังผ่าน `source='manual'` |
| ลูกค้าสแกนช้าจน QR หมดอายุ | กดออกใบใหม่ ใบเก่าตายเอง ไม่ต้องทำอะไร |
| กดออก QR แล้วลูกค้าเดินไปแล้ว | ปล่อยไว้ หมดอายุใน 10 นาทีเอง |

#### ปิดกะ

หน้าสรุป: QR ที่ออกไป / ถูกสแกนจริง / รางวัลที่จ่ายไป

ตัวเลข **"ออกแล้วไม่มีคนสแกน"** คือสัญญาณที่มีค่าที่สุด — ถ้าสูงผิดปกติ
แปลว่าพนักงานกดออก QR แล้วไม่ได้ยื่นให้ลูกค้าจริง หรือยื่นแล้วลูกค้าไม่สนใจ
ทั้งสองกรณีต้องแก้ที่หน้าร้าน ไม่ใช่ที่ระบบ

#### หน้าจอทั้งหมดที่ต้องทำ

`เข้าด้วย PIN` → `หน้าหลัก (2 ปุ่มใหญ่)` → `แสดง QR + สถานะ` → `QR รับรางวัล + สถานะ` → `สรุปกะ`

ห้าหน้า ทุกหน้าออกแบบให้กดด้วยนิ้วโป้งมือเดียว ปุ่มใหญ่ ตัวอักษรใหญ่
เพราะใช้งานตอนมือเปียกและร้านเสียงดัง

#### ต่างจากสาขาที่มี POS ยังไง

สาขาที่ทำ POS เองในอนาคต **ไม่ต้องใช้เว็บพนักงานเลย** — POS เรียก `POST /v1/tokens`
เองตอนปิดบิล แล้วแสดง QR บนจอ POS ระบบสแตมป์ไม่รู้และไม่สนใจว่าใครเป็นคนเรียก
เพราะเว็บพนักงานก็เรียก API เส้นเดียวกันนี้ ไม่มีทางลัดพิเศษ (§10)

### ข. เช็คบัตร

ริชเมนู "บัตรของฉัน" → หน้าเดียวกัน แสดงบัตรใบปัจจุบัน สิทธิ์ที่ค้าง ประวัติ 20 รายการ
เข้าจากเว็บนอก LINE ก็ได้ ล็อกอินด้วย LINE Login เหมือนกัน

### ค. รับรางวัล — พนักงานโชว์ QR ลูกค้าสแกน

1. สแตมป์ถึง checkpoint → สิทธิ์เกิดเอง → LINE เด้งแจ้ง (จุดเดียวที่ push)
2. ลูกค้ามาที่ร้าน พนักงานกด **"รับรางวัล"** → QR ขึ้นบนจอพนักงาน
3. ลูกค้าสแกนด้วยกล้อง LINE — **ท่าเดียวกับตอนสะสมแต้ม**
4. บนมือถือลูกค้า: รายการสิทธิ์ที่ใช้ได้ → **แตะเลือกอันที่ต้องการ → ใช้ทันที**
5. จอพนักงานขึ้น "✓ ให้โค้กฟรี 1 ขวด กับคุณพิมพ์" → หยิบของให้

**ไม่มีขั้นจอง ไม่มีรหัส 6 หลัก ไม่มี dialog "แน่ใจไหม?"**
การยืนยันคือการที่พนักงานส่งของให้ ไม่ใช่ปุ่มบนหน้าจอ

ทำไมทิศทางนี้:

- ลูกค้าไม่ต้องเรียนรู้ท่าใหม่ — สแกนจากจอพนักงาน ท่าเดิมที่ทำมาแล้วสิบครั้ง
- พนักงานกดปุ่มเดียว ไม่ต้องพิมพ์อะไร
- **เครื่องพนักงานไม่ต้องมีกล้อง** รักษาคุณสมบัติ "ไม่ต้องมีอุปกรณ์พิเศษ"
- **ลูกค้าเลือกเองว่าจะใช้สิทธิ์ไหนก่อน** ซึ่งเป็นการเลือกที่ควรเป็นของลูกค้า
  (อาจอยากเก็บหมาล่า 300 กรัมไว้ แล้วเอาโค้กก่อน)

**เรื่องของหมด:** เจ้าของกดปิดตัวเลือกนั้นในหน้าแอดมิน → หายจากรายการของลูกค้า
ทันทีทุกสาขา ดีกว่าให้พนักงานคอยจำว่าอะไรหมด

**กดพลาดแก้ได้:** พนักงานกด "คืนสิทธิ์" ได้ภายใน 10 นาที (`void_redemption`)
แทนที่จะเอา dialog ไปขวางทุกคนเพื่อกันคนส่วนน้อยที่กดพลาด ทางเดินปกติจึงไม่มีอะไรมาขวาง

> **ทำไมข้าม dialog ยืนยันได้อย่างปลอดภัย:** ลูกค้าจะมาถึงขั้นเลือกได้
> ต้องสแกน QR ที่พนักงานเพิ่งกดออกจากเครื่องที่สาขานั้น แปลว่ายืนอยู่หน้าเคาน์เตอร์จริง
> ต่างจากการให้กด "ใช้สิทธิ์" ในแอปได้ทุกที่ทุกเวลา ซึ่งจะเจอเคสกดเล่นที่บ้านแล้วสิทธิ์หาย

## 5. ช่องทางให้สแตมป์

| ช่องทาง | ลูกค้าอยู่ไหน | กลไก |
|---|---|---|
| กินที่ร้าน | หน้าแคชเชียร์ | QR บนหน้าจอพนักงาน |
| สั่งกลับบ้าน มารับที่ร้าน | หน้าแคชเชียร์ | เหมือนกันทุกอย่าง |
| เดลิเวอรี่ Grab / LINE MAN | ที่บ้าน | ส่งรูปใบเสร็จเข้าแชท → เจ้าของอนุมัติ |
| เดลิเวอรี่ทาง LINE OA ร้านเอง | ที่บ้าน | ปั๊มอัตโนมัติตอนปิดออเดอร์ (ยังไม่ทำ) |

### QR ใช้ครั้งเดียว

QR เก็บแค่ลิงก์ `https://liff.line.me/{LIFF_ID}?t={รหัสสุ่ม 16 ตัว Base32}`
ความปลอดภัยอยู่ฝั่งเซิร์ฟเวอร์ทั้งหมด — ถ่ายรูป QR ไปก็ไม่มีประโยชน์ถ้ารหัสถูกใช้แล้ว

หัวใจคือให้ฐานข้อมูลตัดสินว่าใครมาถึงก่อน:

```sql
UPDATE earn_tokens SET status='consumed', ...
 WHERE code=$1 AND status='active' AND (expires_at IS NULL OR expires_at > now())
RETURNING ...;   -- 0 แถว = ถูกใช้ไปแล้ว
```

**ไม่ต้องใช้ Redis หรือ distributed lock** — Postgres ล็อกแถวให้เอง

### เดลิเวอรี่: ส่งรูปใบเสร็จเข้าแชท

ลูกค้าถ่ายหน้าจอใบเสร็จในแอป Grab ส่งเข้าแชท LINE ร้าน → เจ้าของกดอนุมัติ → สแตมป์ขึ้น

**เหตุผลที่เลือกวิธีนี้:** ลูกค้าส่งข้อความมาเอง แปลว่าระบบรู้ LINE userId ทันที ไม่ต้อง
พิสูจน์ตัวตนซ้ำ ซึ่งเป็นต้นตอความยุ่งของทุกวิธีอื่น และมันลบปัญหาเหล่านี้ทิ้งหมด:

- Grab ปิดบังเบอร์ลูกค้า → ไม่ใช้เบอร์
- เลขออเดอร์ฝั่งร้านกับฝั่งลูกค้าอาจไม่ตรง → ไม่ใช้เลข
- ต้อง export CSV / พนักงานคีย์ → ไม่ต้องทำเลย
- ลูกค้าหาเลขออเดอร์ในแอปไม่เจอ → ถ่ายรูปง่ายกว่า

**ไม่ใช้ฟอร์ม LIFF** เพราะจะกลายเป็น 9 ครั้งที่ต้องกด ส่วนแชทคือ 4 ครั้งในหน้าจอที่คุ้นที่สุด
และไม่ต้องถามสาขา/แพลตฟอร์ม (มีไว้ดูสถิติเท่านั้น คนอนุมัติเห็นโลโก้ในรูปอยู่แล้ว)

**ข้อความตอบกลับอัตโนมัติต้องครอบคลุมทั้งคนขอสแตมป์และคนถามคำถาม:**

> ได้รับรูปแล้วครับ 🌶️ ถ้าเป็นใบเสร็จเดลิเวอรี่ สแตมป์จะขึ้นภายใน 24 ชม.
> — ถ้ามีเรื่องอื่นสอบถามได้เลยครับ

ข้อความตอบกลับไม่กินโควตา (§9)

### หน้าอนุมัติ

การ์ดเรียงตามเวลา แสดงรูป + ชื่อลูกค้า + สถานะบัตร + **ธงเตือน**
ใบที่ไม่มีธงกดรวดได้ ("อนุมัติทั้งหมดที่ไม่มีธง") ใบที่มีธงค่อยดูละเอียด

กรองอัตโนมัติก่อนถึงมือคน (ไม่ต้องใช้ AI):
- รูปซ้ำ — SHA-256 ตรงกับที่เคยอนุมัติ → ตีกลับ (บังคับด้วย unique index)
- เกินเพดานสัปดาห์นี้ → ตีกลับ
- ไฟล์ไม่ใช่รูป → ตีกลับ

> **หมายเหตุ:** ต้นทุนการป้องกันไม่ควรแพงกว่าความเสียหาย ที่ของรางวัลต้นทุน 200 บาท
> ต่อ 10 ดวง = 20 บาท/ดวง ถ้าเดือนแรกพบว่าเดลิเวอรี่น้อยมาก การตรวจอาจไม่คุ้ม
> ให้เก็บตัวเลขก่อนแล้วค่อยตัดสิน

## 6. ตัวตนลูกค้า และการกันโกง

### ไม่มี OTP ไม่เก็บเบอร์โทร

บัญชี LINE ปลอมได้แค่ **บัตรเปล่า** — ไม่มีโบนัสสมัคร ทุกดวงยังต้องมาจากบิลจริง
หรือรูปใบเสร็จที่ผ่านการอนุมัติ **บัญชีปลอมจึงไม่ได้กำไรอะไรเลย**
และบัญชี LINE ผ่านการยืนยันเบอร์โดย LINE มาแล้ว

**ไม่รองรับการกู้บัญชีที่ลูกค้าทำ LINE หาย** — เป็นเรื่องนอกการควบคุมของร้าน
ถ้าจำเป็นจริง เจ้าของปั๊มให้ด้วยมือผ่าน `source='manual'`

ผลพลอยได้: ไม่ต้องใช้ผู้ให้บริการ SMS และ **ภาระ PDPA ลดลงหนึ่งชั้น**
เพราะไม่เก็บข้อมูลที่ระบุตัวบุคคลได้โดยตรง เหลือแต่ `userId` ที่เป็นรหัสนิรนาม
ใช้ได้เฉพาะกับ OA ของเรา

### มาตรการกันโกง

| ช่องโหว่ | วิธีปิด | ค่าตั้งต้น |
|---|---|---|
| ถ่ายรูป QR ส่งต่อในกลุ่ม | อายุสั้น + เคลมครั้งเดียว | 10 นาที |
| คนเดียวเคลมรัว ๆ | **ไม่จำกัด** — ซื้อ 10 ออเดอร์ได้ 10 ดวง | `null` |
| ตระเวนสแกนทั้งวัน | **ไม่จำกัด** — QR ผูกกับบิลจริงอยู่แล้ว | `null` |
| ขอสแตมป์เดลิเวอรี่ถี่ผิดปกติ | เพดานต่อคนต่อสัปดาห์ | 3 ครั้ง/สัปดาห์ |
| พนักงานออก QR ให้คนไม่ได้กิน | ผูก `issued_by` + รายงานรายวัน | เตือนที่ 1.3× ค่าเฉลี่ยกะ |
| ส่งรูปใบเสร็จซ้ำ | unique index บน `image_hash` | บังคับที่ระดับ DB |
| พนักงานจ่ายรางวัลผิด checkpoint | `confirm_entitlement()` ตรวจว่าของเป็นของ checkpoint นั้น | บังคับในฟังก์ชัน |
| ยิง API ตรงจากภายนอก | ตรวจ LIFF access token ทุกครั้ง | ดูด้านล่าง |

> **ห้ามเชื่อ `lineUserId` จาก request body เด็ดขาด** ใครก็ปลอมได้ในสามวินาที
> ต้องรับ access token จาก `liff.getAccessToken()` แล้วเซิร์ฟเวอร์เอาไปแลกตัวตนกับ
> `api.line.me/v2/profile` ทุกครั้ง — นี่คือช่องโหว่ที่พบบ่อยที่สุดในระบบที่ทำบน LIFF

**ไม่มีเพดานต่อวัน ไม่มี cooldown** — ลูกค้าซื้อกี่ออเดอร์ก็ได้สแตมป์เท่านั้นดวง

แนวป้องกันของหน้าร้านคือ **ตัว QR เอง**: ทุกดวงต้องมีพนักงานกดออก QR จากบิลจริง
จะได้ 10 ดวงก็ต้องสั่ง 10 บิลและจ่ายเงิน 10 ครั้ง — กลไกจึงจำกัดตัวเองในตัว
โดยไม่ต้องมีเพดานมาช่วย ส่วนกรณี QR ถูกถ่ายรูปส่งต่อ ปิดด้วยอายุ 10 นาที
บวกกับใช้ได้ครั้งเดียวอยู่แล้ว

ที่ยังคงเพดานไว้คือ **เดลิเวอรี่** เพราะรูปใบเสร็จไม่ได้ผูกกับการกดของพนักงานเหมือน QR
คนส่งรูปเข้ามาเองได้โดยร้านไม่ได้ทำอะไรเลย

ทุกค่าอยู่ใน `app_settings` ถ้าเดือนแรกพบว่าตัวเลขผิดปกติ เปิดเพดานกลับมาได้ทันที
โดยไม่ต้องแก้โค้ดหรือ deploy

ตัวเลขทั้งหมดอยู่ในตาราง `app_settings` แก้จากหน้าแอดมินได้ ห้ามฝังในโค้ด

## 7. สถาปัตยกรรม

```
LIFF (ลูกค้า) ─┐
เว็บพนักงาน ────┼─→ Next.js (App Router) ─→ Postgres (Supabase)
หน้าแอดมิน ─────┤     หน้าเว็บ + API          ตรรกะแกนอยู่ในฟังก์ชัน DB
POS (อนาคต) ───┘     ในโปรเจกต์เดียว        ─→ LINE Platform
                                            ─→ Object Storage (รูปใบเสร็จ)
```

| ชั้น | เลือกใช้ | เหตุผล |
|---|---|---|
| เว็บ + API | Next.js 15 + TypeScript | ทุกหน้าและ API อยู่ในโปรเจกต์เดียว ดีพลอยครั้งเดียว |
| โฮสติ้ง | Cloudflare Workers | ชั้นฟรีใช้เชิงพาณิชย์ได้ (Vercel Hobby ห้าม) |
| ฐานข้อมูล | Supabase (Postgres) | ชั้นฟรี 500 MB พอไปหลายปีที่ 5 สาขา |
| เข้าถึง DB | ไดรเวอร์บาง ๆ (`postgres`) ไม่ใช้ ORM | ดีไซน์พึ่งการล็อกแถวที่ควบคุมแม่นยำ |
| ตัวตนลูกค้า | LINE Login ผ่าน LIFF v2 | ไม่ต้องเก็บรหัสผ่าน |
| ตัวตนพนักงาน | PIN 6 หลัก ผูกสาขา | เปลี่ยนกะบ่อย เพิกถอนง่ายกว่าอีเมล |

**ของที่ตั้งใจไม่ใช้:** Redis · ระบบสต็อกของรางวัล · งานหมดอายุสแตมป์ ·
แอปมือถือ · microservice · ผู้ให้บริการ SMS

## 7'. การ deploy — เว็บเดียว โดเมนเดียว

ทั้งระบบเป็น **Next.js โปรเจกต์เดียว deploy ครั้งเดียว** ไม่มีเว็บแยก ไม่มีเซิร์ฟเวอร์เสริม

```
https://<โดเมน>/            หน้าแรก / LIFF ลูกค้า
https://<โดเมน>/staff       เว็บพนักงาน (PIN)
https://<โดเมน>/admin       หน้าเจ้าของ
https://<โดเมน>/api/...     API ทั้งหมด + LINE webhook
```

แยกด้วย route group ใน Next.js (`app/(liff)`, `app/(staff)`, `app/(admin)`)
ไม่ต้องใช้ subdomain — ความปลอดภัยมาจากการตรวจสิทธิ์ ไม่ใช่จากการซ่อน URL

### ที่ที่ต้องไปตั้งค่า มี 5 แห่ง

| # | ที่ | ตั้งอะไร |
|---|---|---|
| 1 | ผู้ให้บริการโดเมน | จดโดเมน ชี้ DNS มาที่โฮสติ้ง |
| 2 | Cloudflare Workers (หรือ Vercel) | deploy โปรเจกต์ + ใส่ env |
| 3 | Supabase | ฐานข้อมูล + bucket `receipts` เก็บรูปใบเสร็จ |
| 4 | LINE Developers Console | Messaging API channel + LINE Login channel + LIFF app |
| 5 | LINE OA Manager | ริชเมนู ข้อความทักทาย ตอบกลับอัตโนมัติ |

ข้อ 5 เป็นงานของคนที่ไม่แตะโค้ด (§14) ส่วนข้อ 4 ควรเป็นของเจ้าของโปรเจกต์คนเดียว
เพราะมี channel secret

### URL ที่ต้องกรอกข้ามระบบ

| กรอกที่ไหน | ค่า |
|---|---|
| LIFF Endpoint URL (ข้อ 4) | `https://<โดเมน>/card` |
| Webhook URL (ข้อ 4) | `https://<โดเมน>/api/line/webhook` |
| ปุ่มริชเมนู (ข้อ 5) | `https://liff.line.me/<LIFF_ID>` |
| ในตัว QR สะสม (สร้างจากโค้ด) | `https://liff.line.me/<LIFF_ID>?t=<รหัส>` |

**ต้องเป็น https ทั้งหมด** LINE ไม่รับ http แม้ตอนพัฒนา — ระหว่างพัฒนาใช้ ngrok
หรือ Cloudflare Tunnel เปิดพอร์ตออกมาชั่วคราว

## 9. ฝั่ง LINE

**ต้องสร้าง:** LINE OA (บัญชีเดียวใช้ทุกสาขา) · Messaging API channel ·
LINE Login channel + LIFF app (size `Full`, เปิด `Scan QR`, scope `profile` + `openid`) ·
ริชเมนู 6 ช่อง · Webhook รับ `follow` และรูปใบเสร็จ

### กลยุทธ์โควตาข้อความ

แพ็กเกจ Free ให้ราว 300 ข้อความ/เดือน กฎคือ:

- **ไม่ push ตอนได้ดวงปกติ** — ลูกค้าเห็นบัตรบนหน้าจอทันทีหลังสแกนอยู่แล้ว
- **push เฉพาะตอนถึง checkpoint** — 3 ข้อความต่อบัตร 1 ใบ (ช่อง 6, 8, 10) ไม่ใช่ทุกครั้งที่มา
- **ไม่มีข้อความเตือนหมดอายุ** — เพราะสแตมป์ไม่หมดอายุ ตัดก้อนใหญ่สุดออกไปเลย
- **ข้อความตอบกลับไม่กินโควตา** — ใช้ auto-reply ให้เต็มที่

## 10. API สำหรับ POS ในอนาคต

**เว็บพนักงานไม่มีทางลัดพิเศษ** ทุกอย่างที่หน้าเว็บทำได้ ทำผ่าน API ชุดเดียวกันนี้
เมื่อ POS พร้อม แค่ออก API key ให้สาขานั้น ไม่ต้องแก้อะไรในระบบสแตมป์

| Endpoint | ใช้ตอน |
|---|---|
| `POST /v1/tokens` | POS ปิดบิล |
| `POST /v1/tokens/{code}/void` | ยกเลิกบิล |
| `POST /v1/stamps` | POS รู้ตัวลูกค้าแล้ว ปั๊มตรง |
| `GET /v1/entitlements/{code6}` | พนักงานคีย์รหัสจอง |
| `POST /v1/entitlements/{code6}/confirm` | เลือกของแล้วยืนยัน |
| `GET /v1/branches/{id}/daily` | ปิดกะ |

Auth: API key ต่อสาขา (เพิกถอนแยกได้) + `X-Idempotency-Key` จำคำตอบเดิม 24 ชม.

## 12. แผนการทำ

**เฟส 1 (~3 สัปดาห์)** — ใช้งานจริงที่สาขาเดียว
LINE OA + LIFF + ริชเมนู · schema + constraint · QR โหมด A + เว็บพนักงาน ·
หน้าบัตรลูกค้า + ใช้สิทธิ์ · หน้าแอดมิน · เพดานต่อคนต่อวัน

**เฟส 2 (+2 สัปดาห์)** — ขยายครบทุกสาขา
หลายสาขา + รายงานรายสาขา · เดลิเวอรี่ (webhook รูป + คิวอนุมัติ) ·
ชุดกันโกงครบ · ตรวจยอดรายคืน

**เฟส 3** — เชื่อม POS และการตลาด
API key ให้สาขาที่ทำ POS เสร็จ · แคมเปญ checkpoint พิเศษ · ส่งข้อความแบ่งกลุ่ม

> **ก่อนเปิดใช้จริง** ทดลองกับพนักงานหนึ่งกะเต็ม สิ่งที่มักพังไม่ใช่โค้ด
> แต่คือพนักงานลืมยื่น QR ตอนเก็บเงิน วัดอัตราสแกนต่อบิลสัปดาห์แรก
> ถ้าต่ำกว่า 30% ปัญหาอยู่ที่หน้าร้าน ไม่ใช่ที่ระบบ

## 13. PDPA และความเสี่ยง

**ข้อกำหนดขั้นต่ำ:** ขอความยินยอมตอนสมัคร (บันทึกเวลาใน `consent_at`) ·
เก็บเท่าที่ใช้ (userId, ชื่อ, รูปโปรไฟล์ — ไม่มีเบอร์โทร) · มีปุ่มลบบัญชี ·
พนักงานหน้าร้านเห็นได้แค่สถานะบัตรกับชื่อ · บันทึกการเข้าถึงใน `audit_logs`

| ความเสี่ยง | ท่าที |
|---|---|
| สิทธิ์ค้างสะสมไม่มีวันหมด | แสดง "สิทธิ์ค้างรับทั้งระบบ" บนหน้าแอดมินทุกเดือน |
| เน็ตร้านล่ม สแกนไม่ได้ | จดเลขบิล ผู้จัดการปั๊มย้อนหลังได้ 7 วัน |
| ลูกค้าทำบัญชี LINE หาย | **ไม่รองรับ** — นอกการควบคุมของร้าน |
| ไม่มีขั้นต่ำต่อบิล | คุมด้วยเพดานต่อวัน ดูตัวเลขเดือนแรกแล้วค่อยตัดสิน |
| เงื่อนไขแพลตฟอร์มเดลิเวอรี่ | ลูกค้าเดินมาหาเราเอง ปลอดภัยกว่าแนบใบปลิว แต่ควรอ่านสัญญาผู้ขาย |
| ผู้ให้บริการชั้นฟรีเปลี่ยนเงื่อนไข | ใช้ Postgres มาตรฐาน ย้ายได้ด้วย `pg_dump` |

## 14. แบ่งงานสำหรับทีม 2 คน

**เจ้าของโปรเจกต์เขียนงาน Next.js ทั้งหมดเอง** อีกคนรับงานที่ไม่แตะโค้ดเลย
ส่งมอบเป็นไฟล์ภาพ / ข้อความ / ตาราง

| ก้อน | รายละเอียด |
|---|---|
| **LINE OA Console** | ริชเมนู · ข้อความทักทาย · **ตอบกลับอัตโนมัติตามคีย์เวิร์ด** · ตั้งค่าบัญชี · ขอโล่น้ำเงิน |
| **งานออกแบบ** | ดวงสแตมป์ (ติด/ว่าง/checkpoint) · mockup หน้าบัตร · ภาพของรางวัล · ป้ายหน้าร้าน |
| **เขียนข้อความ** | ทุกปุ่มทุกหน้าจอ · **ข้อความตอนผิดพลาด** · สคริปต์พนักงาน · คู่มือ · นโยบายความเป็นส่วนตัว |
| **เนื้อหาระบบ** | รายการของรางวัลจริง + ต้นทุน · ตำแหน่ง checkpoint · รายชื่อสาขา/พนักงาน |
| **ทดสอบ** | test case เป็นตาราง · ทดสอบบนมือถือหลายรุ่น · ทดลองหนึ่งกะเต็ม · เทรนพนักงาน |

การตอบกลับอัตโนมัติมีมูลค่าจริง ไม่ใช่งานปะผุ — ข้อความ reply ไม่กินโควตา
ต่างจาก push ทุกคำถามที่ auto-reply ตอบได้คือโควตาที่ประหยัดไว้

**จุดที่ต้องรอ:** ริชเมนูต้องใส่ LIFF URL ซึ่งมาจากฝั่งโค้ด — ออกแบบและตั้งค่าไปก่อน
แล้ววางลิงก์ทีหลังเป็นขั้นตอนสุดท้าย

**LINE Developers Console ควรเป็นของเจ้าของโปรเจกต์คนเดียว** เพราะมี channel secret
กับ access token อยู่ตรงนั้น ส่วน LINE OA Manager เพิ่มเป็นผู้ดูแลร่วมได้
